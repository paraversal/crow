# H4 batch 6: finding #27 (100k frames over 50 ms)

Status: plan only. The executing agent fills in `h4-6.progress.md`.

## Why the earlier batches didn't close it
Batches 3–5 each took the slowest *tracing span* in a live seed-505 run, fixed it, and re-ran. The run went from 399 slow steps (worst 1560 ms) to 72 (worst 110.9 ms). What's left has no single cause, and 51 of the 72 steps have **no span at all**. Chasing spans one by one has stopped working. Two changes in approach:

1. **Measure by sampling, not spans.** Spans only show what someone thought to wrap.
2. **Fix the pattern, not each instance.** Almost every item in #27 is the same shape: a 100k-sized collection keyed by `PathBuf` gets fully cloned, hashed or scanned on the main thread when one small thing changes. Examples: `selected_bytes` and `selected_entries` (`folder.rs:456`, `:479`) rescan every row and hash every path whenever `selection_generation` bumps; 100k clipboard, trash and undo path clones; prune and `select_when_present` in `listing apply` (`folder.rs:1003`).

## Steps
1. **Profile.** Run the seed-505 replay (the script in the #27 support folder, `--script … --until <step>`, `CROW_FUZZ_SHRINK_SECS=0`) on 3–5 of the worst no-span steps under `samply record` (or Instruments Time Profiler). Aggregate self-time by function across those steps. Write a ranked table into the progress file **before changing code**. Keep each run under 30 s, per the fuzzer budget.
2. **Share instead of clone.** Turn 100k path lists that cross owners (clipboard, trash/undo records in `crow_fs::ops`, drag payload, `SelectionEntries`) into `Arc<[PathBuf]>` (or `Arc<Path>` items), so a hand-off is a refcount bump. `SelectionEntries` is already an `Arc`. Follow it to wherever it gets turned back into a `Vec`.
3. **Keep selection aggregates up to date as the selection changes.** Store `(bytes, folders, count)` next to the selection and update it in `toggle`/`select_only`/`clear`/`select_all`/prune, instead of rescanning on a generation bump. `select_all` sets the totals in one pass that already exists. If the selection model lives in `crow-core`, put this there with unit tests. Optionally, store a selected index set (bitset over `entries`) alongside the path set, so display-order scans skip path hashing.
4. **Move the remaining `listing apply` work off the main thread.** Today it does `sync_children` + `rebuild_rows` + selection restore + `select_when_present` (17–37 ms). Build the new rows and the restored selection in `background_spawn` from an `Arc` snapshot, then swap them in on the main thread. Drop the result if the listing generation moved on in the meantime. Only the swap and `cx.notify()` stay on the main thread.
5. **Leave render, text shaping, and Settings/path-bar first render** until step 1's table shows they matter. If they do, cache shaped text per name. Don't rebuild Settings on open.

Stop after each step and re-run only the affected seed-505 steps. Do not do a fresh 10-minute run until steps 2–4 have landed. Bench against `main` (listing, scroll and first paint are all touched).

## Decided (user, 2026-11-16)
- Step 4's one-frame delay before a watcher change shows up is fine.
- The limit is the live fuzzer's `SLOW_MS` (`fuzz_live.rs:31`): how late a 16 ms main-thread heartbeat runs, i.e. how long the UI froze during one step. 250 ms or more fails the run. Limits: 50 ms for scroll, navigation, typing and single-item ops; up to 100 ms for 100k bulk ops (select-all, then copy/cut/paste/trash/undo). #27 closes when a seed-505 run has no step over its limit. The batch-5 run still had steps up to 110.9 ms, so the 100 ms limit is not met yet either; steps 2–4 should close that gap. Telling bulk steps apart in the live runner's report (e.g. tagging steps that act on more than 10k paths) is part of this batch.
