## Decisions
- Branch from `main` @ ad64d27 (H1 #30 and H2 #31 merged). — plan.
- **Spike, FSEvents (2026-11-15):** an ordinary create reports only the child path; removing and recreating the watched root reports the root path itself (3×) and then the new children. `stat_changes` ignores the root (`snapshot.rs:30-37`), so the new children are added while the old rows stay. Spike reverted. — measured.
- #6 sanitizes at the display boundary only; `Entry.name`, matching, operations and the rename field's content stay raw, so a no-op rename cannot change a name. — code convention + Q2.
- #7 should map a root event to `FolderChange::Rescan` in `crow-fs/src/watch.rs`, not add a special case in `Folder`. The watcher callback runs off the main thread, so it may canonicalize to match the resolved `/private` form of an event path against the temp-dir form of the folder path. — cause + AGENTS no-main-thread-I/O.
- #7 fixes both directions of the path-form mismatch: `watch_folder` resolves the watched path once on the watcher's thread (no main-thread I/O) and maps a root event to `Rescan`; `stat_changes` canonicalizes the folder once and matches a child event in either form. — same cause family; without the second half a pane opened through a symlink would still drop every child event (found along the way below) — measured + code convention.
- #8: fix the invariant, not the app; the second window is legitimate. — plan row + H7 ownership of Settings.
- #8 cause differs from the plan's hypothesis: the violation was in the first window, not a non-key one. A filter and a rename field were both open, and the invariant allowed only the one `text_focus_handle` returned (the filter). Guarding focus checks on `window.is_window_active()` was measured to be wrong: the test platform reports every window inactive, so it would silently disable every focus check in fuzzing. Fixed by allowing both pane text handles; the second window stays covered by `a_second_window_keeps_the_focus_invariant`. — measured (GPUI focus trace, minimal repro) — user's ASK item #8 stays "fix the invariant"; this is that fix, with a different cause.
- #9: a sort requested while a folder is loading restarts the load; a background re-sort applies only to the listing it was computed from (same `Arc`), otherwise it re-sorts the newer listing (two tries, then relists). — the in-flight load sorted with its captured order, and an unconditional apply wipes the newer listing — code convention + user (Q3: fix in batch 1).
