Audience: an implementing agent. Follow `.claude/skills/execute-plan/SKILL.md`; read `AGENTS.md`, `docs/testing.md` and the spec's principle 8 ("Theme, icons, keymap and settings are files you own", `docs/Crow — Product & Technical Spec.md`) first.
Base: branch `m6.5-settings` from `main`. Progress file: `docs/plans/m6.5-settings.progress.md`.
PR title: "M6.5: settings window". Don't merge.

**Before writing any code, ASK the user every question in "Questions to ASK" that the plan marks as open.** The recommended answers are recommendations, not decisions.

## Why
`settings.toml` now holds about fifteen choices, several of them visual (theme, app icon, motion, font) that are easier to pick when you can see them. Today ⌘, opens the file in whatever app owns `.toml`; if none does, it fails with a status-line message. A settings window makes Crow approachable without giving up principle 8. **The file stays the single source of truth**: the window reads `Settings` from `Ui`, writes each change into `settings.toml` (comments kept), and follows edits made in a text editor.

It comes before M7 on purpose. M7's fuzzer (H1), accessibility pass (H7) and main-thread I/O guard (H5) then cover the new window, instead of it arriving after hardening untested.

## Current state (main + the housekeeping branch)
- **⌘,** `actions.rs:172` binds `OpenSettings`; `menus.rs:94` opens `settings.toml` with `crow_macos::open_in_default_app` and shows a status-line error when no app owns `.toml`. Crow ▸ Settings… is that action (`menus.rs:49`).
- **Settings model:** `crow_core::Settings` (`crates/crow-core/src/settings.rs`): `theme`, `keymap`, `hints`, `motion`, `sound`, `app_icon`, `font_family`, `font_size`, `show_hidden_files`, `show_preview`, `palette_recent_commands`, `view_per_folder`, `[window] width/height`. `DEFAULT_SETTINGS` is the documented default file, and a test checks that it parses to `Settings::default()`.
- **Writing:** `crow_core::save_setting` (string) and `save_bool_setting` (bool) edit one top-level key through `config::edit_toml`, keeping comments. There is no number or nested-table writer yet (`font_size`, `[window]`).
- **The write pattern to reuse:** `ui::set_show_preview` (`ui.rs` ≈ 388) sets the value in `Ui` at once, then `write_config(SETTINGS, …)` writes off the main thread and reloads; a failure goes to the status line through `ui.set_error`. `ui::set_theme`'s save works the same way.
- **Live reload:** `ui::reload_config` runs on any change in the config dir: settings, menus, feedback (motion and sound) and the Dock icon (`refresh_app_icon`). A broken file keeps the last good settings and shows the error (`Ui::load_settings`).
- **Controls that exist today (all one-offs):**
  - a `Role::Switch` pill in search (`search.rs` ≈ 1190, `search-skip-switch`);
  - radio-button view toggles (`window.rs` ≈ 985);
  - radio and checkbox rows in the motion lab (`motion_lab.rs` ≈ 678–735);
  - `TextInput` (`text_input.rs`).

  There is no drop-down, segmented control or stepper.
- **Theme picker:** an overlay in the window (`window.rs` `ThemePicker` ≈ 138, `show_theme_picker` ≈ 1781). Moving the cursor previews a theme, Return keeps it, Esc reverts. It lists themes off the main thread.
- **Second windows:** `motion_lab.rs` opens its own GPUI window (`WindowOptions`, `TitlebarOptions`), a model for a non-browser window.
- **App icons:** `ui::app_icon_png(AppIcon)` returns the embedded 1024 px PNGs, usable as previews.

## Items

### I1 The window
**Change:** `crates/crow-app/src/settings_window.rs`.
- ⌘, and Crow ▸ Settings… open one Settings window. If it is already open, they bring it to the front.
- It is a normal titled window (title "Settings"), fixed width, sized to its content per Q2. ⌘W and Esc close it.
- It follows the current theme and font like the browser windows do.
- It never opens a browser window and is not a tab.
- It isn't saved with the session; reopening Crow doesn't reopen it.

**Tests:**
- ⌘, opens one window, and a second ⌘, focuses it instead of opening another.
- ⌘W closes it.
- With the window open, a browser window's own ⌘, still works.

### I2 Shared controls
**Change:** `crates/crow-app/src/controls.rs`, styled with theme roles only. Each control is a function returning an element, plus a small state type where it needs one.

| Control | Role and aria | Keys | Used for |
| --- | --- | --- | --- |
| `switch` | `Switch`, `aria_toggled` | Space toggles | booleans |
| `segmented` | `RadioGroup` of `RadioButton`, `aria_selected` | ← → move and select, Space/Return select | keymap, hints, motion, sound |
| `tile_choice` | like `segmented`, but each option is an image and a label | ← → | app icon |
| `stepper` | `SpinButton`, value and range in aria | ↑ ↓ ±1, ⇧↑ ⇧↓ ±10, digits typed in its field | font size, window size |
| `text_field` | `TextInput` (exists) | as today | font family if Q4 = free text |
| `choice_list` | `ListBox` of `ListBoxOption`, typing selects by name | ↑ ↓, type to select | theme, font family if Q4 = list |

Every control has a visible label that is also its aria label, plus an optional one-line description under it in `fg-muted`. Tab and ⇧Tab move through the controls in reading order, and the focused control shows the same focus ring as the sidebar cursor. Rebuild the existing search switch and toolbar view toggles on `controls.rs` only if it's a pure refactor with no visual change; otherwise leave them and record it in the progress file.

**Tests:**
- One keystroke test per control: focus by Tab, operate with each listed key, and check the emitted value and the aria state.
- A layout test: the focus ring never resizes a control.

### I3 What the window shows
Sections follow Q2; contents are fixed here. Each row is a control from I2, bound to one key of `settings.toml`. The description texts are short versions of that key's comment in `DEFAULT_SETTINGS`, which stays the long reference.

**Appearance**
- **Theme:** `choice_list` of "System" plus the index's themes, dark then light, as in the picker. Moving the cursor previews the theme in every window; leaving the list keeps the choice. Extract the picker's listing and preview code instead of copying it.
- **App icon:** `tile_choice` with the four embedded PNGs at 64 px. Description: the Dock switches now, and Finder after the next `scripts/bundle.sh`.
- **Font:** family per Q4, and size as a `stepper` from 10 to 24.

**Behaviour**
- **Keymap:** `segmented` Finder | Vim, with one line describing what Vim adds.
- **Key hints:** `segmented` Auto | Always | Off.
- **Show hidden files:** `switch`.
- **Show preview:** `switch`.
- **Folders keep their own view:** `switch` (`view_per_folder`).
- **Remember recent commands in ⌘K:** `switch` (`palette_recent_commands`).

**Motion & sound**
- **Motion:** `segmented` Auto | Off | Low | Full. Auto says which mode it resolves to now ("Full; Reduce Motion is off").
- **Sounds:** `segmented` Crow | Finder | Off, with a "Play" button that plays the trash sound in the chosen set.

**New windows**
- Width and height `stepper`s, 600 to 4000 points.

**Files** (bottom row, buttons)
- "Edit settings.toml…" (today's ⌘, behaviour, the same failure message).
- "Show config folder in Finder".
- One line naming what the window doesn't cover: `sidebar.toml`, `views.toml`, `exclude.toml`, each a link that opens the file.

### I4 Writing
**Change:**
- `crow_core`: add `save_number_setting(dir, key, f64)` and a nested-table writer for `[window]`, for example `save_table_number(dir, "window", "width", 900)`. Both keep comments like `save_value`, and both get unit tests next to `saving_a_bool_setting_writes_a_bool`. Integers stay integers and `font_size` keeps its `.0`.
- `ui.rs`: one `set_setting(change: SettingChange, cx)` used by every control. It applies the change to `Ui.settings` at once (so the window, menus, feedback and Dock respond in the same frame), then `write_config(SETTINGS, …)` writes it off the main thread.
- `set_show_preview` and `set_theme` route through it too, so there's one write path.
- A stepper's or text field's change writes when the field commits (Return, focus loss, or the arrows). It doesn't write per keystroke.

**Rules:**
- No disk I/O on the main thread.
- Never rewrite the whole file. Change only the key that changed: a value the user typed by hand next to it, and its comment, survive.
- If the change is the default value, write it anyway (don't delete the line); a comment may be explaining it.

**Tests:**
- Each control writes its key and nothing else. Compare the file before and after: every other line, comment and blank line is unchanged.
- A reload after the write doesn't flip the control back (no flicker or loop).

### I5 Following the file
- An edit made in a text editor updates the window through the existing watcher and `reload_config`. Each control re-reads `Ui.settings` on render, so no extra wiring should be needed.
- **A broken `settings.toml`:** the window shows the same error the status line does (file and line) in a banner at the top, with "Edit settings.toml…". Controls stay usable per Q6.
- A key with a value Crow doesn't know (`motion = "slow"`) is part of the broken-file case above.

**Tests:**
- External edits: write `keymap = "vim"` with `write_config` (the test helper); the segmented control shows Vim. Delete the line and it shows Finder.
- Broken file: the banner appears, and fixing the file clears it.

### I6 Reaching it
- ⌘, opens the window (I1).
- A ⌘K command "Settings" does the same.
- A ⌘K command "Edit settings.toml" opens the file directly, for people who prefer the text.
- The theme picker (⌥⌘T) stays as the quick in-window switcher. Its "Apply to All Apps" (⌘Return) stays in the picker only; whether the window offers it too is Q3.
- Add both new commands to `palette::COMMANDS` with stable keys; the existing tests for unique and stable command keys cover them.

### I7 Accessibility
- The window's root has `Role::Group` labelled "Settings". Each section heading is a `Heading` at level 2.
- Every control has a role, label and state as in I2, and every button has a label.
- VoiceOver reads a segmented control as "Motion, Auto, 1 of 4, selected".
- Test: walk the window's controls and assert each has a non-empty label and a role (this is the invariant M7 H7's fuzzer will reuse).

## Questions to ASK
1. **Window, sheet or overlay?** Recommended: its own window, as on macOS (⌘, opens one Settings window for the app). An overlay inside a browser window, like the theme picker, would tie settings to one window and hide that window's content.
2. **Layout: one scrolling page with section headings, or a sidebar of sections (like System Settings)?** Recommended: one page about 560 pt wide, since there are about fifteen controls. A sidebar is worth it from about forty settings, for example once `sidebar.toml` or `views.toml` move in.
3. **Theme: an inline list in the window, or a button that opens the existing ⌥⌘T picker?** Recommended: inline list with live preview, reusing the picker's code. Should the window also offer "Apply to All Apps"? Recommended: yes, as a button under the list.
4. **Font family: free text, or a list of installed fonts?** Recommended: a list ("System" first, then installed families from `NSFontManager.availableFontFamilies` through a new `crow_macos` function, called off the main thread if it's slow), with type-to-select. Free text lets a typo silently fall back to the system font.
5. **Should the window cover `sidebar.toml`, `views.toml` and `exclude.toml` now?** Recommended: no, links only. Each needs its own editor (lists, rules); that's Phase 2 work.
6. **While `settings.toml` is broken, can the window still change things?** `edit_toml` can't edit a file it can't parse. Recommended: controls are disabled (visibly, with the banner explaining why) until the file parses again, so Crow never overwrites a half-typed edit.
7. **Settings that take effect only partly** (window size applies to new windows; the app icon shows in Finder only after a rebundle): is a one-line description under the control enough? Recommended: yes.
8. **Name and slot:** "M6.5" between the UI overhaul and M7, its own branch and PR, and M7 waits for it to merge (H1 should see the window)? Recommended: yes.
