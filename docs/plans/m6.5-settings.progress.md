## Decisions
- Own titled window, one scrolling page, 560 pt wide and 760 pt tall content (560×792 with the titlebar). The page scrolls; Tab scrolls the focused control into view. — Q1/Q2 — user.
- Theme is a drop-down with live preview while its menu is open (was an inline list; changed by Q11/Q12); no Apply to All Apps in the window. The picker keeps its Apply to All Apps. — Q3 — user.
- Font family is a drop-down of installed families, plain names (Q11/Q13); `crow_macos::available_font_families` uses `NSFontManager`, which AppKit only answers on the main thread. It is called once when the Settings window opens, never on browser startup. — Q4 + AppKit constraint — user/code.
- Files section links to `sidebar.toml`, `views.toml`, `exclude.toml`; no editors. — Q5 — user.
- While `settings.toml` is broken, every writing control is disabled and the banner shows the file/line with "Edit settings.toml…"; the Files buttons stay usable. — Q6 — user.
- One-line descriptions for partly-applied settings. — Q7 — user.
- `show_hidden_files` is global and persisted: the browser's ⇧⌘. updates `Ui.settings` and writes, and the settings window's switch updates every browser window. Previously the toggle was per-window and not saved. The user confirmed this after review (Q10). — user.
- Drop-down keys (critique): Space, Return or ↑↓ open the menu without changing the value; typing opens it at the match; Return or a click keeps; Esc, Tab away, a click outside, ⌘W or the title-bar close revert. Esc closes the menu first and the window only on a second press. Tab reverting (instead of keeping) matches a click outside and macOS pop-up menus. — critic, from Q12.
- Settings-specific actions (`Up`, `Down`, `Left`, `Right`, `Activate`, `FocusNext`, `FocusPrev`, `CloseSettings`) instead of reusing the browser's `MoveUp/MoveDown/…`; reusing them made `keys::binding_for` pick the Settings binding for browser key labels. — code.
- `TextInput` gained a unique element id (`with_id`) because the three steppers are visible at once; the old fixed `"text-input"` id collided.
- The Settings window's keystroke tests stay in `settings_window.rs` rather than `window.rs`: they need the window's private `ControlId`, cursors and `control_state`, and use the same GPUI test platform. The user approved the deviation after review (Q9). — user.
- The search switch and toolbar view toggles stay as they are: rebuilding them on `controls.rs` would change their look (the search switch carries a label and keycap; the toolbar toggles are icon buttons), so it is not a pure refactor. — plan's I2 condition — code.
- `text_field` is not built: Q4 chose a list of installed fonts, so no free-text field appears in the window; the stepper reuses `TextInput`. — Q4 — user/code.
- The plan's Finish says "commit and push"; the repo's `AGENTS.md`/`execute-plan` skill say the executing agent commits locally and stops at "Ready for critique", and the critic opens the PR. No push or PR from this branch. — repo rules.

## Found along the way
- `keys::binding_for` matches by keystrokes, not the binding's context, so two actions bound to the same key in different contexts can return the wrong key label. We avoided the collision by giving the Settings window its own actions; a proper fix is M7 H8 material. — left alone.
- `TextInput` used one fixed element id for every field; fixed here with `with_id` because the Settings window shows three steppers at once. — fixed in scope.
